# 冻结检索管线与基线（2026-11-06）

本文说明当前冻结版检索的完整路径、参数和基线数字，供之后的事件层和融合实验对照。代码以 `bench/retrievers/frozen_pipeline.py` 和 `bench/frozen.py` 为准；历次决定见 `DECISIONS.md` D-028～D-032。

## 1. 路径

```text
原始消息（只追加，不修改）
  │  清洗（bench/tasks/real_tasks.clean_messages）
  ▼
上色：每批 150 条，相邻批次重叠 20 条，gemini-3.8-flash-high
  │  colors.gemini-3.8-flash-high.jsonl（每个颜色：color_id、msg_ids、summary、labels）
  ▼
局部颜色块（注入单元，边界、顺序、全部消息都保持原样）
  │  B-index：重叠区每条消息只在前一批的匹配颜色里建索引（按消息 ID，不按文本）
  ▼
四路检索，每路取前 5
  ├ BM25 · 颜色摘要（jieba + 习得词）
  ├ BM25 · 颜色原文块
  ├ 向量 · 颜色摘要（qwen3.7-text-embedding-flash，768 维，文档/查询区分，查询带检索指令）
  └ 向量 · 颜色原文块（别名渲染后的原文，前 1000 字）
  │  B-route：每路里，消息全被更靠前的块覆盖的块跳过，往下补位（先取前 30 再截到 5）
  ▼
全局 RRF（k=60）→ 严格按名次打包进 1500 字（打包时同一条消息只算一次）
  ▼
注入原文块（不是摘要）→ 回答模型
```

时间可见性：每个块以最后一条消息的时间为准，只有早于提问时间的块可见；只检索同一个群。

## 2. 开关与复现

| 名称 | `overlap_dedup` | 含义 | 用于 |
|---|---|---|---|
| A | `none` | 原始批次色块 | D-032 之前的所有实验 |
| B | `index+route` | 去重不合并（冻结版） | D-032 之后 |
| B-index / B-route | `index` / `route` | 只做其中一步 | 消融 |

`bench/run_embed_qa.py` 默认用 B，`--overlap none` 复现旧实验。从其他颜色文件（如 merged-v1）跑实验时只能用 `none`，因为那些颜色不是按批次生成的。

`bench/check_frozen_pipeline.py` 是回归检查，不调用任何模型，只读缓存的向量：

| 检查 | DEV-1 | DEV-2 |
|---|---|---|
| `none` 与此前 V2 问答实验的注入块逐条对比 | 590 条，0 处不同 | 586 条，0 处不同 |
| `none` 与 V0（2026-11-05 以前的冻结版）逐条对比 | 590 条，0 处不同 | 586 条，0 处不同 |
| `none` 与离线三方案实验的 A 逐题对比 | 440 题，0 处不同 | 436 题，0 处不同 |
| `index+route` 与离线实验的 B 逐题对比 | 440 题，0 处不同 | 436 题，0 处不同 |

比较的是证据是否进入、注入块数和注入字数三项。

## 3. 基线数字

| | DEV-1 | DEV-2 | 来源 |
|---|---:|---:|---|
| A（V2）证据进入率 | 90.2% | 72.9% | 检索层 |
| **B（V2）证据进入率** | **89.8%** | **72.5%** | 检索层，相对 A −0.5，不显著 |
| A（V2）端到端准确率 | 85.5% | 71.3% | 问答层，三态评分 |
| B（V2）端到端准确率 | 未测 | 未测 | 需要约 680 次新的回答调用 |

B 几乎不改变证据进入率，却改变了约 78% 的注入内容（DEV-1 460/590，DEV-2 467/586）。去重改变了 192 / 644 个块的索引文本，BM25 的全局统计随之变化，各题候选的名次普遍小幅移动。所以 B 的问答层准确率不能从 A 推断，必须补测。

## 4. 给上层用的块清单

`check_frozen_pipeline --manifest` 在运行目录写出 `blocks.B.jsonl`，一行一个注入块：`block_id`（颜色 ID）、`scope`（`group:<代号>`）、`colors_file`、`batch`、`start_ts`、`end_ts`、`channel`、`msg_ids`（注入的全部消息）、`indexed_msg_ids`（B 下进入索引的消息）、`labels`。

| | DEV-1 | DEV-2 |
|---|---:|---:|
| 块 | 828 | 2,451 |
| 索引里少了重叠消息的块 | 192 | 644 |
| 完全不进索引的块（只剩重叠消息） | 39 | 152 |

ID 是研究阶段的 ID；SQLite 库里的行号由 `bench/store` 的 id 对照文件映射。事件层只引用这些块和消息 ID，不复制原文。

## 5. 已知限制

- 上色几乎不主动多色，颜色也不能跨批延续；跨批的同一段语境靠重叠区和 B-index 衔接。
- 检索深度、预算、RRF 参数都在 DEV-1 / DEV-2 上调过，测试集只能在冻结后跑一次。
- 读带聊天原文的 JSONL 时不要用 `str.splitlines()`：原文里的 Unicode 行分隔符会把一行 JSON 切断。要按 `\n` 逐行读。

## 6. 由库供数与上线用法（2026-11-12）

`bench/store/frozen.py` 从 `memory.db` 构建同一条管线，bothost 的 `memory_search` 调用它（D-046）。与研究文件的一致性校验见 `docs/memory-store-migration.md`「向量表与由库供数的冻结检索」：两个 DEV 群各 590、586 行，块和注入文本全部相同。

上线时与实验不同的只有输入和输出两头，检索本身不变：

- **问题**先过本群的代号表（索引里的人名是代号），再检索。问题的向量现取，两次尝试、15 秒超时；取不到时只跑两路关键词，并在结果里说明。
- **结果**按冻结版的块和 1500 字预算选出，显示时换回真实昵称和原话（清洗后的），块头带起止时间。
- **多个群**各自按冻结版检索，各有 1500 字预算，结果按群并列，不做跨群融合（冻结版只定义了同群检索，跨群融合没有基线）。
- **还没上色的消息**（时间在本群最后一条已上色消息之后）不在冻结版的索引里，另由逐条 BM25 查找，单列一节。

改动 `bench/run_abcd.py`、`bench/memory_text.py`、`bench/embed.py` 后，`python -m bench.check_frozen_pipeline` 在两个 DEV 群上仍然全部通过（4fe395：V2 590/590，V0 590/590，分层 A、B 各 440/440；ed14b7：V2 586/586，V0 586/586，分层 A、B 各 436/436）。
