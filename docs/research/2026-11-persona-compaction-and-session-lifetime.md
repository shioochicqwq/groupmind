# 让带人设的模型写压缩摘要；会话寿命的小实验（2026-11-12）

全部是合成群聊，模型 `deepseek-flash`（DeepSeek 直连），dsh 0.2.1-rc.4 `sdk-minimal`。每个做法只跑了一次，是能不能用的检查，不是分数。
运行目录（含插件、指令、驱动脚本、会话日志）在数据目录 `runs/compaction-2026-11-12/`，账本 5 行。

## 1. 结论

- **带人设的模型能自己写摘要，而且可用。** 插件是 `BasicCompactionEngine` 的子类，只改 `summarize()`：消息前缀与平时一轮完全相同，末尾换成一段中文指令（“这些聊天马上要从你眼前拿走，用你自己的口吻写一段只给自己看的备忘”）。压缩后的三个回问（托它记的事、聚餐的时间地点、停电日期和钥匙在谁手里）都答对。
- **内置指令也答对了**，差别在摘要本身：内置的是英文的编程检查点（Primary Request / Files and Code / Next Step …），把系统提示里已有的规则和工作目录路径又抄了一遍；人设版是第一人称中文备忘，带了对人的感觉和打算。输出 577、757 个 token（人设，两次）对 804（内置）。
- **两种摘要都有同一个毛病**：被压缩的范围不含留下的尾巴，所以摘要会把“刚回过的那句”写成“还没回”。人设版另有一处把一句话安到了错的前因上。摘要不是可靠的原文，原文仍要靠 `memory_search`。
- **摘要请求吃到了缓存**：三次的输入里 93%–97% 是缓存命中（未命中 201–419 个 token）。此前记为未验证的两项（真实线路上的压缩、摘要请求是否命中缓存）在 DeepSeek 上成立。
- **dsh 报的 `inputTokens` 不含缓存命中的部分**，命中的在 `cacheReadTokens`。`bothost/harness.py` 现在把它记进用量文件的 `cached`、`compact_cached`。
- **会话寿命**：在同一个上下文上限下，长会话比每天新会话便宜、也不用查库就能接上前两天的事；真正决定花销的是上下文允许长到多大（压缩阈值），不是会话按不按天切。

## 2. 压缩摘要的对比

设置：窗口 20,000，阈值比例 0.3（约 6,000），尾巴 `retainTokens` 150，摘要上限 1,500。脚本是三个人的群聊：托记抢票时间、停电通知、聚餐投票、闲聊，压缩之后回问。

| | 人设口吻（8 轮） | 人设口吻（9 轮） | 内置指令（9 轮） |
|---|---|---|---|
| 压缩次数 | 1 | 1 | 1 |
| 摘要请求：未命中 / 命中 / 输出 | 201 / 5,760 / 757 | 302 / 5,632 / 577 | 419 / 5,760 / 804 |
| 压缩后的回问答对 | 2/2 | 3/3 | 3/3 |
| 回答用量：未命中 / 命中 / 输出 | 8,049 / 61,312 / 2,204 | 5,488 / 67,712 / 1,822 | 7,959 / 103,040 / 1,778 |

内置那次回答的调用数多（26 对 18），是模型在压缩之前就每轮多发了一条消息，与摘要引擎无关。

## 3. 会话寿命

脚本：模拟三天，前两天各 6 轮，第三天 3 轮闲聊加 2 个回问；消息时间戳隔天。两种做法都挂人设摘要引擎、同样的小窗口。宿主加了配置项 `daily_session`（默认 `true`，即现状；`false` 时一个群一个会话）。

| | 每天新会话 | 一个长会话 |
|---|---|---|
| 轮数 / 模型调用 | 17 / 44 | 17 / 34 |
| 冷启动 / 压缩 | 3 / 3 | 1 / 2 |
| 回答输入：未命中 | 22,351 | 11,426 |
| 回答输入：缓存命中 | 178,944 | 140,160 |
| 回答输出 | 4,415 | 3,637 |
| 压缩：未命中 / 命中 / 输出 | 772 / 17,536 / 1,891 | 475 / 12,160 / 1,519 |
| 第三天回问 | 答对，其中一问查了库（7 次调用、22.5 秒） | 答对，直接从摘要答（2 次调用、1.5 秒） |

读法：

- 每次模型调用读到的缓存量就是当时上下文的大小；未命中的只有新进来的行。冷启动那一轮未命中 2,013–2,633（回放的 40 行），普通一轮约 600。系统提示在跨会话时仍是命中的。
- 小窗口下“回放 40 行 + 一天的量”自己就过了阈值，所以每天新会话那边也压缩了 3 次。这是缩小比例带来的，真实窗口下不会这样。
- 每天新会话多出来的未命中输入，一半来自冷启动回放，一半来自第三天那次查库。

### 放到真实规模

两个开发群按天统计（只数条数和字数，不看内容）：

| 群 | 有消息的天数 | 每天条数 中位 / 九成 / 最大 | 每天字数（含昵称和时间）中位 / 九成 / 最大 |
|---|---|---|---|
| 4fe395 | 60 | 109 / 642 / 2,319 | 4,769 / 22,442 / 92,409 |
| ed14b7 | 44 | 279 / 4,405 / 5,820 | 8,140 / 119,981 / 179,968 |

按一个字 0.7–1 个 token 粗估（未校准），普通一天是几千个 token，热闹的一天是两万到十几万。现在的默认是窗口 262,144、阈值约 19 万：

- 长会话加默认阈值：上下文会一直长到近 20 万才压一次，之后每次调用都读这么多缓存。比每天新会话（上下文约等于当天的量）每次调用多读一到两个数量级。
- 长会话加一个接近“一天的量”的阈值（几万）：就是上表右列的情形，比每天新会话省，而且不丢前一天的话头。
- 所以要定的其实是阈值。会话按不按天切，在阈值定了之后影响很小。

## 4. 未验证

- 隔夜之后缓存还在不在。三天是连着跑的；DeepSeek 的缓存保留多久没有查到也没有测。如果隔夜失效，长会话每天第一轮要把整个上下文按未命中重读一次，阈值越大越亏。
- `deepseek-flash` 的真实窗口是不是 262,144（这是宿主的默认值，不是查来的）。
- 多次压缩之后摘要会不会越滚越走样（长会话那次只有 2 次压缩）。
- 真实群聊上的摘要质量。按 D-022，真实聊天不进 dsh，除非用户要求。
- 人设摘要里“感觉”“打算”这类内容对之后说话的影响，没有量过。

## 5. 更新（2026-11-13）：接进 bothost

用户的决定见 D-048：用人设摘要；DeepSeek 上用长会话（用户给的信息：DeepSeek 缓存保留 72 小时，Gemini 的缓存命中很差，走 Gemini 时更适合每天新会话）。

- 插件和指令在 `deploy/dsh/compaction-persona.mjs`、`compaction-persona.md`。bothost 启动时在数据目录写 `compaction.patch.yml` 并排在补丁列表最前面，配置里的补丁仍可覆盖它。
- 补丁里插件的 `name` 不能用 `!!js` 表达式：dsh 会报 `name.startsWith is not a function` 并禁用这一项，只写进 `dsh.stderr.log`。内置引擎此时已被禁用，结果是完全不压缩。前两次复查就是这样白跑的。
- 小窗口测试要另加一份补丁把 `headroomTokens` 调小（默认 65,536，比 2 万的窗口还大）。真实窗口下不需要。
- 按默认接法复查一次：第 7 轮压缩（摘要 522 个输出 token，输入 96% 命中），回问 3/3。
- 暂定值：阈值 30,000，尾巴 1,250（dsh 估算），摘要上限 4,000。真实窗口下没跑过。

## 6. 更正（2026-11-13）：第 3 节的规模估计漏了工具结果

第 3 节「放到真实规模」只按群聊文字算上下文的增长。用户指出：实际使用时工具结果也留在上下文里，比如网页。量了一下现在的工具一次返回多少（只量长度）：

| 工具 | 一次返回的字数 | 依据 |
|---|---|---|
| `memory_search` 冻结版部分 | 每个群中位 1,325–1,355，上限 1,500 | 两个开发群各 590 / 586 条记录在案的结果 |
| `search_web` | 6,002 | 实际调用一次，8 条结果 |
| `search_web` 带正文 | 14,641 | 同上 |
| `fetch_page` | 2,181、3,122、65,013 | 实际抓三个公开网页；没有长度上限 |

- 一次带正文的搜索或一个长网页，就抵得上普通一天的全部聊天。上下文长得多快主要看工具用得多不多，不是看群里说了多少。
- `fetch_page` 没有上限：一个长页面自己就能超过 3 万的阈值，甚至接近整个窗口。定阈值之前要先给它封顶。
- 这次调用顺带确认了联网工具的成功路径（此前因余额不足只见过失败）。

那篇 Telegram 群 bot 的文章（`2026-11-workspace-notes.md` 的来源）给的线上数值，经网页摘要工具读出，未逐字核对：

- 窗口 128K，上下文到约 11 万 token 触发压缩，保留最近约 2 万 token 的原话。
- 窗口开到 256K 的那段时间不再压缩，但每次请求的基础量涨到约 13 万。
- 自写压缩器出过一次故障，约 45% 的模型调用都在做压缩。
- 抽样的 40,593 次请求平均 93,067 个 token，其中聊天历史 86.6%、系统提示 10.2%、压缩摘要 2.1%。
- 压缩之后前缀作废，下一次调用按全价重读。我们的实验里也是这样：压缩后只有系统提示还命中，尾巴和摘要都是未命中。尾巴留得越大，每次压缩越贵。
- 文章没有给出不同阈值的花销对比；它提到一篇论文建议 16K–48K，作者没有试。
- 原始网页不进主上下文：在沙箱里切到几百字再交回，重活放到子会话。

所以第 3 节「阈值接近一天的量」的说法不成立，暂定的 30,000 / 1,250 没有依据，等用户定。

## 7. 用户的决定和子会话探查（2026-11-13）

用户定：阈值和尾巴照文章，约 11 万触发、保留约 2 万原话；联网结果照文章放到子会话里处理。

- 配置已改：`compact_at_tokens` 110,000；`compact_keep_tokens` 5,000（dsh 的估算，按一次测得的约 4 倍折算成 2 万真实 token，折算比例只量过一次）；摘要上限 8,000，写到上限被截断时照用，不让压缩失败。真实窗口下没有跑过。
- dsh 自带的子会话（`dsh-subagent`、`dsh-subagent-spawn-in-process`、`dsh-tool-subagent`）用补丁插进极简档就能加载和运行，不需要改 dsh。一问一次的探查里看到的：
  - 调用是异步的：工具立刻返回子会话编号，子会话结束后主会话收到一条通知并自己开始新的一轮。
  - 不加限制时子会话拿到和主会话一样的系统提示和工具，它自己去调了发群消息（被宿主拒绝）。
  - 主会话手里仍有联网工具，派出子会话的同时自己也搜了一次，49,091 字的结果进了主上下文（16,258 个未命中 token）。
  - 通知引起的那一轮在宿主的一轮之外：用量文件只有一行，那一轮和子会话的用量都没记上。
- 要用它，至少得做三件事：联网工具只给子会话、发消息和人设只给主会话（dsh 的做法是预设，`dsh-agent-preset-registry`，没试）；宿主把通知引起的那一轮算进同一次对话；子会话交回的内容限长。

## 8. 联网查证改由宿主另开对话（用户决定，2026-11-13）

用户在两种挂法里选了宿主同步跑。做法：

- 主会话的 `search_web`、`fetch_page` 换成一个 `look_up(question)`。宿主收到后另开一段没有人设的对话（`bothost/lookup.py`，提示在 `prompt_lookup.md`，同一个模型线路），那段对话自己搜索和读网页，交回结论。
- 上限：每个工具结果 12,000 字，最多 6 次模型调用，整体 90 秒（dsh 工具桥的超时调到 120 秒），结论 800 字截断。这些数是我定的，没有基线。
- 用量单独记：`usage.jsonl` 那一行多一个 `lookup`（调用数、未命中、命中、输出、联网次数、秒数）。
- 没有搜索密钥时不提供这个工具。不带群的 stdio 用法（dsh 网页端的测试会话）没有改，仍是原来两个工具。

合成的两问，各跑一次：

| 问题 | 主会话未命中 | 主会话命中 | 查证未命中 | 查证命中 | 查证输出 | 整轮秒数 |
|---|---|---|---|---|---|---|
| 事实（某版本的发布日期） | 2,609 | 4,864 | 3,325 | 640 | 270 | 7.6 |
| 读一个长网页 | 1,251 | 9,856 | 6,281 | 4,736 | 1,084 | 19.6 |

对照：同一个事实问题让主会话自己搜（第 7 节那次），主会话未命中 19,706。两问都答对了，但只有两问，不能当成效果结论。

要知道的：

- 读长网页那次模型发到群里的一条消息很长，查证的结论被原样展开了，说话方式要另外看。
- 页面 12,000 字以后的内容查证对话看不到，问到页面后半段会答不出。
- `scripts/memory/term_candidates.py` 是从会话日志里的 `search_web` 结果认梗的，群会话里现在只有 `look_up`，这条线在 bothost 的会话上接不上了（未处理）。
