# dsh 测试会话与 bothost 的重合和整合（2026-11-12）

起因：用户指出 dsh 里早就放了测试会话（A-32、A-33），而 A-39 写 `bothost/` 时没有用它，两边有重复。用户批准读取 `~/.dsh/profiles/web/` 下的相关文件后做的调查。测试会话的配置不一定是最终的，目标是把两边整合成一套。

读了：`cordis.patch.yml` 里的 `preset-test` 段、`persona-botname.md`、`persona-botname.mjs`、`memory-tools.mjs`、`web-tools.mjs`，以及仓库里的 `scripts/memory/memory_search.py`、`term_candidates.py`。没有改 `~/.dsh` 下任何东西，没有重启 dsh 网页服务。

## 1. 结论

1. 两边是同一个 bot 的两半。测试会话有「它是谁、知道什么、能查什么」（人设、人物和梗的快照、联网、查历史），但只能在 dsh 网页里一对一聊。bothost 有「怎么进群」（QQ 收发、攒批、是否接话、发送、多群、shell 和工作区），但人设和知识是空的。
2. 真正重复的只有两处：系统提示词怎么拼，和「查聊天记录」这个工具。其余是互补。
3. 测试会话的东西全在仓库外（`~/.dsh/profiles/web/`），写成 dsh 插件，路径写死，换框架或换机器都带不走。整合的方向是：内容和工具归到宿主一侧，dsh 只做模型循环；测试会话改成挂同一套东西的薄壳。
4. 有三件事要用户定（第 4 节），其中两件属于记忆系统的设计，我不替你选。

## 2. 两边各有什么

| 部分 | 测试会话（dsh 网页档的 `test` 预设） | bothost |
| --- | --- | --- |
| 入口 | 人在 dsh 网页或手机上一对一聊 | QQ 群，OneBot 反向 WS |
| 系统提示词 | `persona-botname.md` + `memory_snapshot.md`，由 dsh 插件整段替换 | `bothost/prompt.md`（群聊规矩）+ 可选的人设文件、快照文件，经环境变量给极简档 |
| 「现在」和最近的聊天 | 模型自己调 `memory_context`，拿历史库里最近活跃群的末尾 40 条，把那一刻当作现在 | 每批消息自带时间；新会话带本群最近 40 行 |
| 查历史 | `memory_search`：查 `memory.db`（导入的历史，4 个群，约 9.3 万条），jieba 分词的 BM25，默认**所有群一起查** | `search_chat`：查 `chat.db`（上线后新记的），SQLite FTS5，**只查本群** |
| 联网 | `search_web`、`fetch_page`，直调 DeepSeek 官方接口 | 没有 |
| shell 和工作区 | 没有（预设里只有这四个工具） | 有 |

| 梗表更新 | `term_candidates.py` 从 dsh 会话记录里抽模型查过的词 | 没有接上 |

## 3. 冲突和缺口

**人设文件里混着三种内容。** 前半是性格和说话方式，可以原样用。中间的对话示例标注「来自既有对话」，不能进开源仓库。后半是工具用法，写的是测试会话的工具名和流程（「会话开始先调用 `memory_context`」），到了群里是错的：群里的「现在」来自消息本身，不来自历史库的末尾。另外开头一句是「你和对话者熟识」，是一对一的口吻。

**历史库和新库是两个库，两种查法。** `memory.db` 是导入的历史，只读；它的索引是整库重建的（库一变就要重新分词，约几十秒），接不了实时写入。`chat.db` 是 bothost 自己记的，写一条索引一条，但里面没有历史。bot 上线后，同一个群的旧事和新事会分在两边。两种查法谁准，没有比过。

**跨群。** 测试会话查历史默认所有群一起查，这在一对一测试里没问题。放到群里，等于 A 群的人能问出 B 群的原话。

**联网工具的密钥。** `web-tools.mjs` 在环境变量里没有密钥时，会去读 dsh 自己的凭据文件。bot 放进 WSL 后，本来的设计是 dsh 那一侧只有模型密钥。

**梗表更新接不上。** `term_candidates.py` 写死了去 `~/.dsh/sessions/` 下本仓库的目录找会话，工具名认的是 `search_web` 和 `memory_search`。bothost 的会话在它自己的数据目录里，刚跑完时文件是未压缩的 `session.v4.jsonl`（脚本找的是 `.zstd`；之后会不会被压缩没有确认），工具名带 `mcp__qq__` 前缀。

**路径写死。** 三个插件里的 Python 路径、脚本路径、人设路径都是这台机器的绝对路径。

## 4. 要用户定的三件事

1. **群里查历史，查不查别的群。** 我的建议是默认只查本群，要跨群的在配置里逐群写明。这关系到群友的隐私，你定。
2. **历史库和新库怎么合。** 这是记忆系统的设计，没有可比的基线，我不选。可选的路：
   - 合成一个库，新消息也写进 `memory.db` 的表，索引换成能逐条更新的（FTS5，或者定时重建 BM25）；
   - 两个库都留，查的时候两边都查再合并；
   - 先只接历史库（只读），新消息暂时只靠会话上下文。
   仓库里已经有 FTS5 的评测代码（`tests/bench/test_fts5.py`），可以先在评测集上把 FTS5 和 jieba BM25 比一次再定。
3. **人设是不是就用<BOT_NAME>这份。** 用的话，对话示例和快照都留在 `qqbot-data`，不进仓库；工具用法那一段我按群聊重写后放进仓库的 `prompt.md`。

## 5. 不需要你定、我建议直接做的

- **工具都归到宿主一侧，经 MCP 提供。** 联网两个工具用 Python 重写进 bothost（逻辑很短，就是转发两个接口），密钥留在宿主，不进 dsh。这样换成 Pi 时工具不用动，也不依赖 `~/.dsh` 下的文件。
- **人设拆成三段**：性格和说话方式（文件，仓库外）、群聊规矩和工具用法（`bothost/prompt.md`，仓库内）、快照（文件，仓库外）。bothost 已经能读前两段，这次加了快照的配置项 `snapshot_file`。
- **测试会话改成薄壳**：dsh 网页档的 `test` 预设不再自带三个插件，改成挂 bothost 的工具端口，人设读同一组文件。这样你在网页里试到的，和群里跑的是同一套。这一步要改 `~/.dsh` 的配置并重启 dsh 网页服务，**做之前要你同意**。
- **`term_candidates.py` 加一个会话目录参数**，并认带前缀的工具名。
