# 专属工作区与一篇群聊 bot 文章的借鉴（2026-11-11）

来源：<https://mizore.blog/posts/save-a-little-more/>（作者自己的两个 Telegram 群 bot，三个月的线上数据）。
用户要求：记忆系统仍按我们自己的思路，只看别的可借鉴之处，重点是专属工作区。

本文只是调研，没有改任何配置或代码。AstrBot 部分读的是 v4.29.1 源码和随附文档（提交 `dffe922`），**没有实际部署或运行过沙箱**。

## 1. 结论

1. 文章的「工作区」由三件事组成：一台隔离容器、脚本式工具调用、重活放到子会话。AstrBot v4.29.1 对第一件和第三件有现成支持，第二件没有。
2. 我们现在的配置（D-014）是本机环境、只开工作区读写、禁执行。要得到文章那样的容器，需要把运行环境换成「第三方沙箱」（Shipyard Neo），另起 Docker 服务。
3. 部署目标是 Windows PC（D-021）。AstrBot 的本机隔离不支持 Windows，所以在 Windows 上只有两条路：禁执行（现状），或第三方沙箱。官方建议沙箱宿主机至少 4 核 8 GB。
4. 沙箱执行默认只对 AstrBot 管理员开放。让普通群友也能触发，是一个需要用户决定的安全取舍。
5. 记忆之外另有四条可借鉴：记忆注入的位置、按意思找原文的实测参数、小模型决定是否接话、发送相关的三条规矩。

## 2. 文章里的工作区

| 组成 | 文章的做法 |
| --- | --- |
| 容器 | rootless Docker，独立系统用户；预装 Python（uv）、Node、ffmpeg、ImageMagick、ripgrep、Chromium、中文字体。模型只有读、写、改、bash 四个基本工具 |
| 边界 | 容器里没有任何密钥和环境变量；根文件系统只读；只有 `/work` 可写并保留，每周清空；`/tmp` 是 256 MB 内存盘；内存、CPU、进程数有上限；网络可一键关断；模型请求和发群文件由宿主进程转手，发文件前解析真实路径 |
| 脚本式调用 | 模型写一段脚本：先发一句「稍等」，并行调搜索和查聊天记录，在沙箱里把结果切到几百字再交回主模型。原始网页不进主上下文，主模型只被叫醒两次 |
| 子会话 | 检索、调研、调试放到独立子会话，只把结果带回。主会话只留「大家在聊什么」和「我做了什么」 |

前提是作者自己说的「专用的部署，通用的 Agent」：只服务一个信任的群，才敢给 shell。文中对照的另一个项目面向陌生人部署，就明确不给 shell。

## 3. AstrBot v4.29.1 能做到哪些

### 3.1 运行环境

配置项 `provider_settings.computer_use_runtime` 有三个值（`astrbot/core/config/default.py`）：

| 值 | 含义 | 隔离 |
| --- | --- | --- |
| `none` | 不给任何环境（默认） | 无需 |
| `local` | 在 AstrBot 所在环境直接执行 | Linux 用 bubblewrap，macOS 用 Seatbelt；**Windows 不支持** |
| `sandbox` | 第三方沙箱，独立容器 | 由沙箱服务负责 |

`local` 下按「普通成员 / 管理员」分别设三项：允许执行、允许联网、文件范围（关闭 / 工作区 / 整个环境）。工作区是 `data/workspaces/<会话标识>/`，另可读写 `data/temp/`。

没有本机隔离时（Windows 即此情况），可选组合只剩四种，其中唯一能执行代码的是「整个环境 + 允许执行」，等于不设防（`docs/zh/use/astrbot-agent-sandbox.md`；`astrbot/core/computer/process_sandbox/__init__.py` 里只有 Linux 和 macOS 两个后端）。

### 3.2 第三方沙箱

驱动器三种：Shipyard Neo（默认，推荐）、Shipyard（旧版）、CUA（带截图和键鼠）。文档标注「仍处于技术预览阶段」。

Shipyard Neo 的情况：

- 由三个部件组成：控制面、负责 Python / shell / 文件的容器、负责浏览器的容器。
- 工作区固定在 `/workspace`，由持久卷提供，容器重建后数据还在；默认大小上限 1,024 MB。
- 默认配置档每个沙箱 1 核 1 GB；带浏览器的配置档再加一个 1 核 2 GB 的容器。
- 沙箱按消息会话缓存，同一个群通常复用同一个沙箱；生命周期上限默认 3,600 秒，空闲超时 1,800 秒。
- 控制面需要挂载宿主机的 Docker 套接字。
- 挂载的工具：`astrbot_execute_shell`、`astrbot_execute_ipython`、文件读 / 写 / 改 / 搜索、上传、下载；配置档带浏览器能力时另有三个浏览器工具。

权限：`computer_use_require_admin` 默认开启，非管理员调用沙箱执行会被拒绝（`astrbot/core/tools/computer_tools/util.py` 的 `check_admin_permission`）。文件读写改搜索在沙箱下对普通成员不设路径限制，上传和下载仅管理员可用（`fs.py` 文件头的说明）。

### 3.3 与文章逐项对照

| 文章的做法 | AstrBot v4.29.1 | 依据 |
| --- | --- | --- |
| 独立容器、无密钥 | 第三方沙箱是独立容器；里面有没有环境变量取决于配置档的 `env`，默认为空 | 文档中的 `config.yaml` 示例 |
| 只读根文件系统、去掉全部特权 | **未找到对应配置**，需看 Shipyard Neo 仓库 | 未验证 |
| 资源上限 | 有，按配置档设 CPU 和内存 | 同上示例 |
| 一键断网 | 本机环境有「允许联网」开关（需隔离后端）；沙箱只见代理设置，**未找到断网开关** | 未验证 |
| 工作区定期清空 | 没有定时清空；有空闲回收和孤儿卷清理 | 示例中的 `gc` 段 |
| 把文件发回群 | 有：下载工具加 `send_message_to_user` | `fs.py`、`message_tools.py` |
| 脚本里调用 bot 自己的工具 | **没有**。源码中搜不到同类机制；沙箱里的 Python 调不到搜索、查聊天记录这些工具 | 全仓搜索无结果 |
| 子会话 | 有，标为实验性。主模型得到 `transfer_to_<名称>` 工具，子代理不带主会话的历史，只把结果返回，可后台执行 | `docs/zh/use/subagent.md` |
| 小模型决定是否接话 | 没有。内置的主动回复只有按概率一种 | `builtin_stars/astrbot/group_chat_context.py` 的 `need_active_reply` |

## 4. 对我们的建议（待用户定）

1. **部署前不动**。现在没有部署，D-014 的「本机、工作区、禁执行」先保持。
2. **部署到 Windows 时二选一**：
   - 保持禁执行：没有 shell，视频抽帧之类继续靠插件。
   - 上 Shipyard Neo：需要那台机器装 Docker（Windows 上要经 WSL2），并留出约 2 到 4 GB 内存。D-012 当时放弃沙箱的理由是开发机内存不够，换机器后这个理由需要重新评估。
3. **执行权限先只给管理员**（默认值）。群友能诱导 bot 执行命令，是否对群友开放由用户决定。无论开不开，沙箱里都不放密钥，也不挂真实聊天库。
4. **「先过滤再进上下文」用子代理近似**。AstrBot 没有脚本式调用，但把搜索交给一个子代理，主会话只收到结论，效果接近。代价是多一次模型调用，实际省不省要量。
5. **思路 1 的原文库做成工具**，按发言人、时间、回复关系查，按需调用，不每轮预先注入。AstrBot 已有 `get_group_message_history` 工具可以对照。

## 5. 记忆之外的其他借鉴

1. **注入位置**。文章的规矩：已发出的前缀一个字不改；动态内容只追加在本批消息之后，不进系统提示词，不写回会话库。他们的 DeepSeek 缓存命中率因此是 98.7%。我们思路 2、3 的「印象」文本将来注入时应照此办理。AstrBot 的群聊上下文本来就是追加到用户消息一侧（`req.extra_user_content_parts`），插件可以走同一个口子。
2. **按意思找原文的实测**（对照思路 1）：
   - 窗口 800 字比 1,500 字准，首条命中率 0.81 对 0.76；3,000 字降到 0.62。
   - 去掉 bot 自己的发言，首条命中率从 0.76 掉到 0.48。
   - 相似度分数分不出「没聊过」：相关窗口中位数 0.669，不相关 0.658。
   - 换说法查 25 个话题，20 个首条命中；问「某个梗什么意思」10 次全部查不到。后者正是我们黑话候选（D-039）要补的。
   - 完整一句描述比两三个关键词准。
3. **是否接话**。被 @、被回复、被叫名字用确定性规则；闲聊由只读最近约 6 行的小分类器决定是否叫醒主模型。加 14 个示例后召回从 0.53 升到 0.71。在 AstrBot 上要自己写插件。
4. **发送**。显式的发送工具，发完就结束本轮；网络状态不明时不重发，因为发送不是幂等的；图片识别结果迟到时追加一条，不改旧行。

## 6. 与三个记忆想法的关系

- **想法 1、2**：一致。他们也保留原文，再加一条按意思找的路，返回的仍是原话。
- **想法 3**：他们完全不做加工过的记忆，理由是加工错了会被压缩固化成事实（他们出过一次事故：摘要把臆测当成事实，bot 在群里指责群友）。他们衡量的是准确率，想法 3 本来就不按准确率评，所以不构成否定。
- **可吸取的三条约束**：印象始终挂着原文消息 id（已做到）；印象不再被二次摘要；回答里印象以「我的印象」出现，不当事实陈述。后两条还没写进设计。

文章引的论文已核对存在：Bao 等，*Is Complex Agentic Memory Always Needed? Naive RAG Is Stronger Than We Thought*，arXiv:2610.30755，2026-10-22。摘要称 Raw-RAG 在七组设置中六组第一，领先 0.13 到 5.53 分。文章里「换成原子事实掉 19.62 分」等细项只见于正文，**我只读了摘要，未核对**。
