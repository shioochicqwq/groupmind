# 会话接力：实施报告 v2（2026-11-14）

v1 见 `2026-11-session-handoff-report.md`。本版只写 v1 之后的改动，以及更新后的风险清单。v1 的 T1–T10 结果和 P4 数字仍然有效。

## 1. 起因

用户指出 v1 有两处不对：
1. 通用 agent 内核本来就不该有时间限制。
2. 退休的会话不释放内存，接力次数一多，内存只会越占越大。

## 2. 查到的情况

- **时间限制都是 bothost 自己加的**，dsh 本身没有：
  - 回合 300 秒：串行时，一个卡住的回合会挡住整个群。
  - 工具调用 180 秒：在 `bot.patch.yml` 里设的。
  - 看视频 160 秒后先回「还没看完」：为了躲开上面那 180 秒。

  有了接力，慢任务不再占群聊，这几处限制都失去了理由。
- **v1 说「SDK 没有取消，只能杀进程」不对。** dsh 内部有 `agent.cancel()`，dsh 网页端的取消就用它，插件可以直接调用。
- **内存没释放的原因**：会话由 SDK 服务端打开，它把会话对象一直存在自己的表里，又不提供关闭方法。不过 SDK 会转发进程里所有会话的事件和状态，所以会话完全可以由插件来打开、持有和关闭。

## 3. 改动

| 文件 | 改动 |
|---|---|
| `deploy/dsh/handoff.mjs` | 插件持有会话的 handle，提供 `open`、`prompt`、`fork`、`cancel`、`close`、`stats`；进程退出时 dispose 所有会话 |
| `bothost/harness.py` | 开接力时由插件打开会话、发消息；新增 `close`；`turn(stall=…)` 不限总时长，只做卡死检测（`_watch`） |
| `bothost/app.py` | 开接力时不再有 300 秒上限，也不杀进程；后台任务没有总时长上限；旧会话退休时，以及换日后旧会话空闲时调用 `close`；看视频一次调用等到看完；查证帮手的预算放宽到工具上限以内 |
| `deploy/dsh/bot.patch.yml` | 工具调用上限改由 `QQBOT_TOOL_TIMEOUT_MS` 设置，默认仍是 180 秒 |
| `bothost/watch.py` | `wait=None` 表示等到看完再返回 |
| `bothost/config.py` | 新增 `stall_s`（600 秒）、`handoff_tool_timeout_s`（3600 秒）；删掉 `handoff_task_timeout_s` |

**卡死的判定：** 一个会话 `stall_s` 秒内没有任何事件，而且它当前没有正在执行的工具调用。工具调用是宿主自己在干活，不算停住。判定为卡死时只取消这一个会话，进程和其他会话不受影响。取消后 60 秒内仍没停下，这一回合记为出错，但仍不杀进程。

**关掉接力时**，以上全部不生效，行为与改动前一致。

## 4. 验证

- `tests/bothost/test_handoff.py` 现在有 13 个测试，连跑 3 次都通过；`tests/bothost` 加 `tests/bench` 共 141 个通过。新增的两个：
  - `test_retired_sessions_leave_memory_however_long_the_chain`：连续接力 4 次后，插件里打开着的会话只剩活跃会话一个。
  - `test_no_time_limit_on_a_turn_and_a_stalled_session_alone_is_cancelled`：
    - `turn_timeout_s=1` 时，4 秒的回合照常完成。
    - 模型流挂住，2 秒后只取消那个会话，回合记为 `stalled`。
    - 进程 pid 不变，下一条消息照常回复。
- **内存实测**（`qqbot-data/runs/handoff-2026-11-13/mem_chain.py`）：先发一回合约 40 万字的合成长文本，再连续接力 30 次。

  | 退休会话 | 结束时活着的会话 | 堆用量（随 GC 起伏） | 结束时 RSS |
  |---|---|---|---|
  | 关闭 | 1 个 | 57–151 MB | 262 MB |
  | 不关闭 | 31 个 | 63–149 MB | 290 MB |

  会话数量的差别很明显，但内存数字差得不多。原因是复制出来的会话和原会话共用历史对象（dsh 的 `buildForkSeed` 直接引用原事件），每个退休会话独占的只有它后台那段工具记录；这次测试里那段只有几 KB。真实使用中，查证结果每次可能有上万字，独占的部分会更大，这一点未实测。两种情况下 RSS 都有上涨，看起来是 V8 没有及时把内存还给系统；不是会话泄漏，因为关闭时会话数一直是 1 个。

## 5. 更新后的风险清单（替代 v1 第 5 节）

1. **真实 QQ 群未验证**，引用回复的显示效果也未验证。
2. **dsh web 测试会话不在范围内。**
3. **卡死检测只看会话事件。** 宿主自己的工具如果内部卡住（例如浏览器或下载卡住且没有自己的超时），会话会一直等，因为有工具调用在执行时不算卡死。工具调用上限现在是 1 小时，最终会由这个上限截断。
4. **取消后 60 秒仍没停下**，这一回合记为出错，但会话可能还在后台跑。
5. **调用归属靠参数匹配**，同 v1。
6. **`browser_first` 自动学习可能记错站**，同 v1。
7. **依赖 dsh 0.2.1-rc.4 的内部接口**：`agents.create/resume`、`buildForkSeed`、`agent.cancel`、`createUserMessage`。dsh 升级后要重跑测试。
8. **旧会话的收尾靠模型照格式写**，同 v1。
9. **超时或中断不会在群里自动说一句**，同 v1。
10. **全部改动都没提交。**
