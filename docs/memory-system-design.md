# 长期记忆系统：设计与第一阶段计划

> 状态：**待审阅的设计草案**（2026-11-02），尚无实现。
> 下文「已确认」来自用户逐项确认；「调研」只代表所查资料；「待测」要靠实验决定。
> 系统计划开源：本文和代码不写真实聊天内容；样本与评测数据不进仓库。

## 1. 目标

让 QQ 机器人成为**有记忆的群友**：记得发生过的事，认识群里的人并有自己的印象，在合适的时候自然想起旧事，且不被无关记忆带偏。

- 冲突时的优先级：像群友 > 回答完备。它可以不知道或记不清，但不能编造。
- 不靠一份不断增长的用户摘要；原始记录完整保留，结构化记忆都能追溯到原文。

**核心研究方向**（2026-11-02 确认，D-023）：长期记忆与语义索引；人物、事件及关系认知；多 Agent 按需召回；**持续知识习得与伪学习**；主动知识维护与经验修正。是否采用复杂的多 Agent、自反思、Notebook 或定时心跳，由实验和工程成本决定。

**伪学习的评测目标**：机器人面对原本不了解的知识（网络梗、内部梗、人物典故、新表达），学习历史后能否在新对话中正确理解和运用。设计和实验见 [知识习得调研报告](research/2026-11-knowledge-acquisition-survey.md)。

**第一阶段不做**：接入线上 QQ、接话和爬楼、态度影响回复、主动发话。知识习得**要做离线评测**；后台维护、Notebook 和多 Agent 先离线对照，不预设为必需组件。

## 2. 已确认的需求

| 主题 | 决定 |
|---|---|
| 记忆视角 | 历史视为机器人一直在群里潜水，导入的历史全部算读过 |
| 上线后的消息 | 系统全部入库，但未读的不算它知道 |
| 阅读行为 | 作息、话题兴趣、亲疏、预算共同决定读多少，均可配置；被 @ 时向前翻看语境；被问到未读内容时按意愿决定 |
| 接话 | 记忆也可以触发接话 |
| 主动发话 | 先测试，效果差就不加 |
| 人物 | 维护身份和关系；形成印象和态度，并影响互动意愿；初始印象来自历史，互动后更新 |
| 跨群 | 不设硬边界，内容凭语境判断；对同一个人的态度跨群共用 |
| 身份不确定时 | 先挂起，语境合适时在群里自然地问，也可以问管理员 |
| 上色 | 原文不动；一条消息可以有多种颜色；颜色是检索入口 |
| 颜色结构 | 两层：局部语境 + 长期话题；第二层可能只是向量相近，也可能需要显式关联，待测 |
| 图片 | 用视觉模型结合上下文理解；表情包单独处理 |
| 群友的话 | 是数据，不是指令。删除请求只会停止召回，不删除数据，因为部署者保留数据的权利 |
| 维护 | 可以自动修改派生记忆，但保留历史并可回滚；遗忘只降权，不删除 |
| 通用性 | 不区分会话类型，不绑定模型和人设；先适配 AstrBot 与 dsh + qq-bridge，允许两个版本 |

调研后再定：召回判断方式、索引方式、Notebook、经验来源。测试后再定：投毒处理、全量上色策略。

## 3. 调研依据

### 3.1 保留原文有证据支持
- 一项受控实验中，原文分块明显优于只存抽取结果：LoCoMo 43.9% 对 28.0%，LongMemEval-S 67.4% 对 45.4%（[2601.00821](https://arxiv.org/html/2601.00821v4)）。
- 同一实验中，「原文 + 抽取结果」（42.5%）与只用原文几乎一样。
- 原文分块的弱点是不善于回答「不知道」：LoCoMo 对抗类问题 6.5% 对 15.0%。这说明筛选层和「返回空结果」确实必要。
- **适用范围有限**：这是单次运行、固定一种抽取结构；论文未说明数据是否含多人对话；也没有测试本项目的上色。另一项非正式实验还发现，抽取事实在跨会话问题上有优势（[CommonMemO #62](https://github.com/Mehul-Gupta-SMH/CommonMemO/issues/62)）。

### 3.2 上色与上述结果不冲突，但要验证
**保留原文是为了把原文喂给模型，上色是为了索引出原文块，同时也是原文的分块方式（用户说明）。** 第一层颜色就是「微语境」；人物和时间是原文块绑定的元数据。固定窗口会把交错的对话混在一起，而颜色能把它们分开。上述论文比的是分块和抽取结果，没有回答这个问题，所以要用第 5 节的对照实验衡量提升。各决策点的起点和对照见 [选项登记表](memory-options.md)，它优先于本文后面的旧描述。

### 3.3 交错对话的分离方法
近期较强的方向有两种：让模型把新消息分配给已有的对话簇（[CEUR 论文](https://ceur-ws.org/Vol-4178/paper2.pdf)），或先预测回复关系再做图聚类（[CASCON 2025](https://conf.researchr.org/details/cascon-2025/technical-papers-track/38/Revisiting-Thread-Disentanglement-in-Technical-Chat-with-Fine-Tuned-LLMs-and-Graph-Ba)）。前者与「颜色是可增量更新的对象」最接近，优先尝试。

### 3.4 召回方式
非官方的逆向分析称：ChatGPT 每轮注入预先算好的记忆，Claude 由模型按需调用检索工具（[分析一](https://fcdagdelen.github.io/archive-fever/memory-architectures-frontier-ai)、[分析二](https://lin-guanguo.github.io/llm-memory-research/memory.summary/)）。这些细节未经官方证实，来源之间也有矛盾。

**当前提议（待第二阶段验证）**：组合使用，小而稳定的人物印象随会话带入，具体事件先经低成本检索和筛选，再允许主模型按需调用工具展开原文。

## 4. 架构

```
平台适配器（AstrBot / dsh + qq-bridge）
        │ 消息流、回复上下文
        ▼
记忆服务 ── 阅读层：机器人读到了哪里（第二阶段）
   ├─ 原始层：消息、媒体引用、来源映射（只追加）
   ├─ 派生层：颜色、摘要、人物、说法、印象（有版本、可回滚）
   ├─ 索引层：全文、向量、人物、时间（可随时重建）
   └─ 召回：触发 → 候选 → 筛选 → 注入（第二阶段）
```

记忆服务独立于 Bot 框架，这样才能离线重建和回放评测。适配器尽量薄。

### 4.1 核心数据
| 对象 | 关键字段 |
|---|---|
| `message` | 来源、群、发送者稳定 ID、时间与序号、正文、引用目标、原始记录指针 |
| `media` | 所属消息、类型、文件引用、是否找到文件 |
| `color` | 层级（语境 / 长期话题）、类型、名称、别名、摘要、状态、版本 |
| `color_link` | 颜色 ↔ 消息（多对多）、置信度、作用、由哪个模型版本产生 |
| `person` / `identity` | 稳定身份；昵称、头像、别名及其生效时间；未确认的同一性候选 |
| `claim` | 说话人、对象、内容、类别（本人说、他人说、系统推断、本人确认）、来源消息、时效 |
| `impression` | 对象、内容、依据、更新历史（第一阶段只预留） |
| `read_mark` | 群、读到的位置（历史导入时标记为全部已读） |
| `recall_block` | 被停止召回的对象及操作者 |
| `revision` | 派生数据的每次修改：旧值、新值、原因、来源 |

### 4.2 不变量
1. 原始层不被任何自动流程修改。
2. 每条派生记忆都能追溯到原始消息。
3. 消息内容一律是数据，不能改变系统配置或记忆规则；只有管理员操作能直接改记忆。
4. 系统推断不会自动升级为事实；他人的说法也不等于事实。
5. 索引可以从原始层和派生层完全重建。
6. 代码、测试和文档里没有真实聊天内容、QQ 号或群号。

### 4.3 数据来源
只取主号导出目录。依据其 README，`chatlab_reconciled/` 是引用已校正的推荐版本，因此作为导入主体；原始字段和追溯回查 `raw/`。该 README 只针对导入 ChatLab，不是对本系统的结论，第一步要抽样核实。

- 规模（文档自述）：771,708 条可展示消息、51 个群，2024-10 至 2026-10。
- 不并入 `migration_recovery/`，它只有元数据，没有正文。
- 约 37.6% 的媒体元素找不到候选文件，有候选也未验证内容，系统必须能接受「图丢了」。

## 5. 评测

### 5.1 题目来源
| 来源 | 测什么 | 注意事项 |
|---|---|---|
| 人工题集 | 准确性和理解力，由用户出题 | 数量少；需要来自熟悉的话题 |
| 时间切分回放 | 用时间点之后的真实发言，测能否找到之前的旧事 | 检索不能读取时间点之后的数据 |
| 引用关系 | 约 12.5 万处已验证引用，可用于回放和语境分离 | **必须先清洗**：很多引用不是「想起旧事」，如短距离回复、表情回应或只有 @ 的引用；测试时要去掉引用字段本身以防泄漏答案 |
| 干扰测试 | 同一段对话注入相关、弱相关、无关记忆 | 自动统计强行提及率 + 用户盲评自然度 |

### 5.2 对照组
| 组 | 检索单元 | 作用 |
|---|---|---|
| A | 固定窗口原文，关键词 + 向量 | 对照基线 |
| B | 语境颜色摘要 → 原文 | 验证上色的价值 |
| C | B + 向量相近作为隐式第二层 | 第二层方案一 |
| D | B + 显式长期话题 | 第二层方案二 |

上色是项目的核心设计。A 组用来衡量上色带来多少提升；如果没有提升，先调整上色方法，再决定如何处理。

中文短句、黑话和昵称可能让纯向量检索吃亏，因此关键词检索的分词方式也要比较。

### 5.3 指标
召回率（Recall@k）、排序质量（MRR）、无相关记忆时正确返回空结果的比例、跨日与跨周问题的单独得分、每千条消息的处理费用和用时。

**具体达标线不预先设定**：跑出 A 组结果后，由用户根据数据确定。

## 6. 第一阶段计划

| 步骤 | 内容 | 完成标准 |
|---|---|---|
| 0 | 核对数据：读取 `chatlab_reconciled` 字段定义，抽样对照 `raw/`；统计引用的跨度分布；查明小号数据情况 | 确认导入来源和字段映射；得到引用可用性报告 |
| 1 | 取样本（约 1000 条），放在仓库外或被 gitignore 的目录 | 样本可重复读取，未进入 Git |
| 2 | 建原始层和导入器 | 消息数与原始数据一致；任意消息可追溯；重复导入不产生重复 |
| 3 | 上色试验：语境分配、多色、图片、表情包；比较模型和批大小 | 得到每千条的用量、费用、用时；用户抽查质量 |
| 4 | 取一个群的几周连续记录，建立 A–D 四组和全部评测题 | 评测可一键重复运行 |
| 5 | 运行对照，并确定第二层方案 | 用户根据结果决定方案和全量上色策略 |
| 6 | 干扰测试：选定模型上注入三类记忆，结合盲评 | 决定是否需要抑制机制 |

第 0–3 步可在当前机器进行（样本很小）；第 4 步起如果磁盘不足，再迁移到常驻 PC。全量处理不属于第一阶段，除非第 5 步后用户决定。

## 7. 模型渠道与风险

### 7.1 模型渠道（用户决定）
批处理使用本机的模型网关。

- **实现要求**：渠道必须可替换，严格限速，支持断点续跑，失败时不重试轰炸。

备选：[付费 Gemini API](https://ai.google.dev/gemini-api/docs/pricing)。粗算（假设每条消息 40 tokens，上下文重叠翻倍，输出占输入 30%，**未实测**）：全量上色用 2.5 Flash-Lite Batch 约 $7，2.5 Pro Batch 约 $130，不含图片。

### 7.2 其他风险
| 风险 | 应对 |
|---|---|
| 群友隐私：真实聊天和人物印象会发给云端模型 | 先过滤高敏感内容；样本不进仓库；开源版默认不收集 |
| 跨群凭语境判断可能说漏嘴 | 第二阶段专门加入泄漏测试 |
| 带态度的人物画像被本人看到可能引发冲突 | 第二阶段前不启用；印象不直接外显的规则另行讨论 |
| 公开基准多为两人对话，不代表群聊 | 以自有评测为准 |
| Drive 上聊天数据与 `secrets/`、`decrypted/` 同目录 | 由用户检查共享权限；第一阶段不下载这些目录 |
| 与现有 `memory_beyond` 的职责重叠 | 第一阶段不接线上，不产生冲突；第二阶段再定 |
