# Benchmark 第一轮结果

> 2026-11-02～03，开发集 DEV-1，随机种子 0。被测模型 `gemini-3.8-flash-high`，判官 `gpt-6.1-sol`（都走本地模型网关）。
> 这一轮只有 1 个群、1 次上色、部分起点。下面的数字是第一批证据，不足以定选项。人工打标后再裁决，见「人工打标」。

## 结论

1. **评测框架可信。** GroupMemBench Technology 上的 BM25 总分 44.6%（95% CI 38.5–51.2），论文 46.0%。
2. **上色还没有被证明更好。** 跨周问题上 S0 与 `BM25 + 固定窗口` 无显著差异；词面相近度低的题上领先，但这批题可能偏向摘要。
3. **S0 在引用还原上很差**：R@10 是 1.0%，基线是 12.1%。闲聊短句的细节进不了颜色摘要。
4. **筛选模型是目前最明确的收益**：注入消息从平均 71.2 条降到 10.9 条，准确率未见显著下降。
5. **梗表第一次测出提升**：看不到答案、只按上下文召回时，填词准确率从 10.6% 升到 15.3–17.6%，原文检索没有提升。样本小（85 题、40 个词），词也没人工确认。
6. **模型提取和统计候选打成平手**：建出的表大小相近（34 和 32 条），只重合 13 条，两者是互补的。

上表 knowledge_update 和 user_implicit 按 gemini 判官计。换 gpt-6.1-sol 重判后，两项变为 27.8 和 28.6，总分仍是 44.6（CI 38.0–51.2），两个判官 99.1% 一致。

## Q1：引用还原（DEV-1，1,957 题）

**这个题型不能当长期记忆的主分。** 清洗后 97% 的引用发生在 1 小时内，跨日只有 1 条（共 2,391 条引用）。另外两个规模相近的群的分布也一样。

| 配置（jieba，只用回复本身作查询） | R@10 全部 | R@10 1小时–1天（55 题） |
|---|---:|---:|
| 颜色摘要 → 原文块（S0） | 1.0% | 5.5% |
| 颜色原文块（I3 对照） | 1.9% | 9.1% |
| 固定窗口 10 条（基线） | 12.1% | 18.2% |

切词和窗口大小的影响都很小。

早期「带最近 3 条原文」的 R@1 曾到 37%，这是假象：这些消息和目标落在同一窗口。现在框架把屏幕上已有的消息排除在记忆之外。

## 主实验：检索对象 × 交给模型（DEV-1，2026-11-03）

440 道跨周题，其中 105 道经人工复核，335 道新出且未复核；另有 150 道在答案出现前再问一次，测拒答。判官 gpt-6.1-sol（与人工一致率 99.6%）。所有组注入前去重，窗口相邻的合并成连续片段。

| B | 颜色摘要 | 摘要 | 是 | 50.0%（45.5–54.5） | 46.0% | 61 |
| C | 颜色摘要 | 原文块 | 是 | 65.7%（61.4–70.0） | 59.0% | 237 |
| D1 | 两路 RRF | 原文块 | 是 | **73.6%（69.5–77.7）** | 66.0% | 280 |
| D2 | 两路 RRF，筛选看摘要 + 原文 | 原文块 | 是 | 72.7%（68.6–77.0） | 67.0% | 301 |

| 比较 | 有筛选 | 同为 1500 字 |

| B 只给摘要 − A | **−20.2（−25.5，−14.8）** | **−20.9（−26.6，−15.5）** |

| D 两路合并 − A | **+3.4（+0.2，+6.1）** | +0.9（−2.7，+4.8） |
| D2 重排 − D1 | −0.9（−4.1，+2.0） | |
| D − 基线 | **+9.8（+4.5，+14.8）** | **+5.0（0，+9.8）** |
| A − 基线 | **+6.4（+1.6，+10.9）** | **+4.1（+0.5，+7.7）** |

| 5 条窗口 − 10 条窗口 | | **−4.8（−8.4，−1.1）** |

结论：

- **只给摘要不行**（B 比 A 低约 20 个百分点）。检索层「摘要命中率最高」是假象，摘要丢了答案细节。R4 起点「喂原文块」得到确认。
- **搜原文块优于搜摘要**（C 比 A 低 3–5 个百分点），I3 起点「搜颜色摘要」应改为搜原文块，或者两路合并。
- **两路合并（D）最好**：有筛选时显著优于只搜原文；同为 1500 字时与 A 打平。让筛选模型同时看摘要（D2）没有额外收益。
- **颜色块优于窗口**：同为 1500 字时 A 高 4.1、D 高 5.0 个百分点，词面重叠低的题差距最大（66% 对 57%）。
- **筛选是用准确率换注入量**：A 有筛选时只注入 291 字，准确率 70.2%；填满 1500 字时 74.3%。答案存在时筛选清空了约 22% 的结果。
- 拒答率各组都在 91–96%，差别不大。
- 被安全拦截的调用：回答 81 次、筛选 131 次，各组可见题里有 3–15 题回答为空，按答错计。335 道新题没有人工复核。

## 向量检索（I4–I6，2026-11-04）

向量模型 `qwen3.7-text-embedding-flash`（阿里云百炼，768 维）。原文块只取前 1000 字嵌入；查询和文档同一向量空间。各组都按 1500 字预算、不筛选；A、D、窗口基线与主实验共用缓存，结果相同。Gemini 免费层每天只能嵌入约 1000 段，所以没有使用。

| 组 | 检索 | DEV-1 | DEV-2 | DEV-1 低重叠 | DEV-2 低重叠 |

结论：

- **向量单独用不如关键词**，搜摘要的向量最差。
- **改进合并比加向量更重要**：每路保底 3 块就把 D 提高约 4 个百分点。原来的 RRF 会把单路排在前面的块挤掉，这与「A、C 至少一路答对」的上限分析一致。

- 加入向量后拒答率略降（92–95% → 89–90%），因为向量总能返回结果。
- 嵌入用量：两个群共约 0.97M token（按接口返回的实际数）。

## 打包与保底（E1–E4，2026-11-04）

每路只取前 10 个候选；四路是关键词两路加向量两路，两路只有关键词。1500 字预算，不筛选。

| 组 | 打包方式 | DEV-1 四路 | DEV-2 四路 | DEV-1 两路 | DEV-2 两路 |
|---|---|---:|---:|---:|---:|
| E1 | 全局 RRF，严格按名次 | 82.1% | **70.0%** | 80.4% | 63.1% |
| E2 | 各路轮流取 | **82.7%** | 69.3% | 80.4% | 64.4% |
| E3 | 每路预留 预算÷路数，再按 RRF 补齐 | 58.2% | 52.1% | 76.1% | 61.7% |
| E4 | 按 RRF 分数 ÷ √新增字数贪心 | 71.4% | 57.8% | 66.4% | 52.5% |

配对差值（百分点，95% CI）：

| 比较 | DEV-1 | DEV-2 |
|---|---:|---:|
| E2 − E1（四路） | +0.7（−2.0，+3.4） | −0.7（−3.7，+2.1） |
| E2 − E1（两路） | 0.0（−2.5，+2.3） | +1.4（−1.1，+4.1） |
| E3 − E1（四路） | **−23.9** | **−17.9** |
| E4 − E1（四路） | **−10.7** | **−12.2** |
| E1 四路 − E1 两路（向量的贡献） | +1.6（−2.0，+5.2） | **+6.9（+3.4，+10.3）** |

结论：

- **候选深度才是上一轮「被挤掉」的主因**。同样是严格按 RRF 打包，每路从 30 个候选缩到 10 个，四路从 79.8% / 66.3% 升到 82.1% / 70.0%，关键词两路从 75.2% 升到 80.4%（DEV-1）。原因是 RRF 对「在多路里都排得很靠后」的块累计加分，候选越深，这类块越多，会排过只在一路排第 1 的块。上一轮的保底只是在弥补这个问题。
- **轮询（E2）与全局 RRF（E1）打平**：候选深度合适后，路线顺序偏差已不明显。
- **E3、E4 的退化来自长度偏差，是实现问题**：E1 答对而它们答错的题里，绝大多数是证据所在的长块被丢掉了（E3 四路：DEV-1 113 题中 104 题、DEV-2 86 题中 70 题；被丢块字数中位数 541–586）。颜色块字数中位约 170，但 18–23% 超过 375 字，E3 每路只预留 375 字，最好的长块放不进；E4 用 √字数做惩罚，偏好短块。两者注入块数都从约 8 块升到约 15 块。
- **向量的贡献在 DEV-2 显著**（+6.9），DEV-1 不显著（+1.6）。

证据在候选里却没被注入的比例（挤出率）随 K 单调上升：DEV-1 为 4.1% → 5.5% → 8.0% → 10.2% → 10.7%，DEV-2 为 6.7% → 7.6% → 14.5% → 20.0% → 22.7%。证据在候选里的比例也在上升（DEV-2 76.4% → 90.8%），但两者相抵，最终进入注入的比例在 K5 最高。只要证据进了注入，准确率在各 K 下都稳定在 92–95%。所以 K 影响准确率几乎完全靠一件事：证据能不能挤进 1500 字。

机制：

- **RRF 尾部会挤掉单路第一名。** K10→K30 时被挤出的题里，证据块大多在某一路排第 1，但只出现在一两路；它的融合名次从 2–12 名掉到 6–33 名（DEV-2 的 20 题中，每题的证据块都在某一路排第 1）。单路第 1 的 RRF 分是 1/61 ≈ 0.016；一个在两路都排第 12 的块得 2/72 ≈ 0.028。候选越深，这种「多路都排得一般」的块越多，就会把只有一路找到的强证据挤到 1500 字之外。
- **K 小时，这些块的位置由尾部让出来。** K3 相比 K10 救回的题，证据块的融合名次从 3–17 升到 2–11。代价是有的证据只在某一路排第 4–10 名，截断后就丢了。K3 在 DEV-2 上因此退化 3 题，K5 只退化 1 题。
- **两边都有证据时，K 小注入更干净。** K5 在证据前面的干扰字数比 K10 少 12（DEV-1）到 43（DEV-2）字，平均块数也少；K20 和 K30 则多 11–23 字。这类题的救回和退化大致相抵，不是 K 起作用的主要途径。

结论：

- **K3–K10 是一个平台**，两个群上两两之间都不显著（|差值| ≤ 1.4 个百分点）。**K20 及以上明显变差**：DEV-2 上 K20、K30 都显著低于 K10，K20 显著低于 K5；DEV-1 方向一致，但不显著。
- **选 K5。** 它在 DEV-2 上最高、在 DEV-1 上与最高的 K3 差 0.2 个百分点，证据进入率在两个群都最高。它也比 K3 稳：K3 在 DEV-2 上丢独有证据，比 K5 低 1.4 个百分点（不显著）。K5 和 K10 的差异不显著，选 K5 的理由是挤出率更低、跨群一致，而不是准确率更高。
- 这是 DEV 上的探索性结果，K 是在同一批题上挑的。确定方案后应冻结，再到独立 TEST 集上验证。

## 人工打标

打标页由 `bench/labeling.py` 生成：每人一个离线 HTML，不需要账号或服务器，手机也能用。

| 卡片 | 做什么 | 用途 |
|---|---|---|
| 检查题目 | 合格 / 合格但问法别扭 / 答案不对 / 证据不够或有歧义 / 更像梗或常识 | 把跨周问题升为 GOLD；「问法别扭」的题保留，另算一版不含它们的结果 |
| 判断回答 | 对 / 部分对 / 错 / 题目本身有问题 | 校验判官，用人工判定重算各配置 |
| 梗词条 | 群内特有或通用 × 解释对或错 / 人名外号 / 不是梗 | 校验 K1、K4 和解释质量 |
| 自己出题（可选） | 写问题和答案，搜出证据 | 不偏向摘要的 Q6 题目 |

第一轮 3 份，每人约 133 张卡，其中三类各 20 张重叠用来算一致性，重叠共 60 张。结果放进 `returned/` 后合并：

```bash
python -m bench.labeling merge --labels <labels>/round1/returned --runs <runs>/real-dev --out <labels>/round1
```

输出标注人一致性（Cohen's kappa）、需要裁决的冲突、判官与人工的一致率、各配置按人工结果重算的准确率、词条质量和人工新出的题。

- 用人工结果重算后，配置排序不变：搜颜色原文块 73.3%、不筛选 72.4%、S0 69.5%、基线 64.8%。相对基线都不显著（搜原文块 +8.6，CI −1.9～+19.0）。

- 52 个词：说法 47、人名外号 4、不是梗 1（「白洲」由用户裁定为人名）。说法里解释对 38 个（80.9%），本群特有 8、通用 39。真正属于这个群的梗很少。
- 用户的最终裁定写在打标目录的 `rulings.json`，合并时优先于投票。

### A + B

两人重叠的 20 张卡上，按真正影响结论的维度比较：

| 维度 | 一致 |
|---|---:|
| 题目能否当考题（合格或问法别扭 vs 其他） | 20 / 20 |
| 回答对或不对 | 18 / 18 |
| 词条解释对不对（A 在备注里纠正的算「不对」） | 15 / 17 |
| 词是本群特有还是通用 | 9 / 17 |

直接按原选项算的 kappa 很低（题目 0.35、词条 0.16），主要差在两点：「合格」与「问法别扭」之间的取舍，以及 A 用的旧选项没有「人名或外号」。**本群特有还是通用的界线因人而异**，不适合作为自动评分的硬标准。判官与人工合计 166 次判定一致率 99.4%。

## 更正：「多色」几乎全部来自批与批的重叠（2026-11-05）

阶段报告写「被覆盖的消息中 13.8%（DEV-1）/ 13.3%（DEV-2）属于多个颜色」。逐批核对后发现，**同一批之内**一条消息属于多个颜色的只有 3 条（DEV-1，约 0.0%）和 30 条（DEV-2，约 0.1%）。其余 1,565 条和 4,187 条都是相邻两批重叠的 20 条消息被上下两批各上了一次色。

所以：

- 提示词允许多色（C1「可自由多色」），但模型实际上几乎不这样做。
- 重叠区会产生两个内容相近的颜色。注入时消息去重了，但检索时这两个颜色会互相竞争候选位置。

这与 idea 的设计有出入，需要人工看样本后决定怎么改。审阅页在仓库外的 `qqbot-data/review/` 下。

- **dedup-v1 修掉了重复，代价不显著**：准确率在两个群上都低了约 1 个百分点，但不显著。一种可能的解释是，重复的两个颜色原来相当于给同一段语境多了一个被检索到的机会；去重后，后一批的颜色少了重叠部分，文字变短，命中也变少了。【解释，未证实】
- 曾提议采用 dedup-v1，**用户叫停，不采纳**（D-031）。dedup-v1 删掉了后一批颜色里的重叠消息，改变了原始色块的边界。
- **根本问题没有解决**：模型几乎不主动多色，颜色也不能跨批。这要从上色本身改，比如把上一批还没结束的颜色带进下一批，让模型续上；或者在提示词里更明确地要求多色。这需要重新上色（两个群约 440 次 Gemini 调用）。
- 花费：新调用 Gemini 1,051 次（回答），判官 122 次；新色块的向量约 0.5M token。

## 重叠重复与分层：三方案离线实验（2026-11-05，只测检索层）

固定条件：冻结版 V2 向量、四路、每路前 5、全局 RRF（k=60）、严格按名次装入 1500 字，交原文块。**不调用 Gemini。** 色块边界都保持原样，注入单元始终是原始批次的色块（`bench/run_color_layers.py`）。

| 方案 | 做法 |
|---|---|
| A 原方案 | 原始批次色块 |
| B-index | 建索引时，重叠区的每条消息只计入一个色块（前一批的匹配色块）；后一批的色块建索引时不含这些消息，但注入时仍是原块 |
| B-route | 每路候选里，一个块的消息如果全部已经出现在排名更靠前的块里，就跳过它、往下补位；任何消息都不会因此丢失 |
| **B 去重不合并** | B-index + B-route |
| C 分层 | B，再加一层全局话题：相邻批次对同一语境上的色块合成一个话题，话题同样走四路检索；局部块加上所属话题的 RRF 分，每个靠前话题里最好的局部块也进入候选；注入的仍是局部块 |

| | DEV-1 证据进入 | 相对 A | DEV-1 候选池 | DEV-2 证据进入 | 相对 A | DEV-2 候选池 |
|---|---:|---|---:|---:|---|---:|
| A | 90.2 | — | 95.5 | 72.9 | — | 82.1 |
| B-index | 89.8 | −0.5（−1.8，+0.7） | 95.7 | 72.5 | −0.5（−2.1，+1.1） | 82.8 |
| B-route | 90.2 | 0（没有一道题变化） | 95.5 | 72.9 | 0（没有一道题变化） | 82.1 |
| **B** | 89.8 | −0.5（−1.8，+0.7） | 95.7 | 72.5 | −0.5（−2.1，+1.1） | 82.8 |
| C | 90.5 | +0.2（−1.4，+1.8） | 96.1 | 71.6 | −1.4（−3.7，+0.9） | 84.2 |

A 复现了冻结版 V2 原来的证据进入率（90.2% / 72.9%）。四条路的 R@5 在各方案之间的差都在 ±1.4 个百分点以内，只有 C 的话题向量路例外，比 A 低 3–6 个百分点。原因可能是长话题在嵌入时被截到前 1000 字。

**结论**：

1. **重叠造成的重复上色，几乎不影响检索。** 去掉重复、但不改变色块边界（B），证据进入率的变化在 ±0.5 个百分点以内，不显著。B-route 在两个群上没有改变任何一道题：完全被更靠前的块覆盖的重复块，几乎从不出现在每路前 5 里。【证实，检索层】
2. 所以「多色 13%」主要是**统计口径造成的假象**，不是检索上的缺陷。当前的四路 RRF 和打包时的消息去重，已经消化了这种重复。
3. **分层（C）没有带来改进**：候选池变大了（+0.6 / +2.1），但证据进入率没有提高，DEV-2 上还略有下降（不显著）。话题分数会把长话题里的块排到前面，挤占了预算。
4. **建议**：冻结版保持原始上色（A），不做后处理去重。真正的结构问题有两个：模型几乎不主动多色，颜色也不能跨批延续。这两个问题应当在上色阶段解决，比如把上一批还没结束的颜色带进下一批，让模型续上，再用这套检索层实验来评估。
5. 台账新增 10 行（每个群 5 个方案），B 和 C 在「切块」一栏注明与此前实验条件不同。

### 采用 B 与研究发现（用户决定，2026-11-05）

冻结版改用方案 B（去重不合并：B-index + B-route，D-032）。**从此起，冻结版的检索条件与此前所有实验不同**：此前的实验都用方案 A，结果保留不改。B 只在检索层测过（证据进入率 89.8% / 72.5%，相对 A 为 −0.5，不显著），问答层还没有测。

> **研究发现**：本研究发现，LLM 批次上色过程实际表现出近似单标签的局部语义分段特征。其检索效果主要依赖局部片段结构，而非跨批次重复标注。将局部片段合并为全局长块会显著降低证据注入率，而对重复进行去除、保留局部边界的方案未观察到明确的性能损失。这提示语义主题组织与证据检索单元应分别设计和评估。

## 梗基线：没有梗表时模型能否解释（DEV-1，2026-11-05）

`bench/run_term_baseline.py`。参考答案是两轮人工打标确认过的含义，共 71 个词：通用层 56 个，本群层 15 个，按 D-033 分层。参考文件在仓库外（`qqbot-data/labels/term_refs.v1.json`）。回答模型 gemini-3.8-flash-high，不带任何记忆；判官 gpt-6.1-sol，判「对 / 错 / 不知道」。参考给出了具体所指（某种药、某个人）而回答只给大类，算错。

| 条件 | 词数 | 全部 | 通用层 | 本群层 | 回答「不知道」 |
|---|---:|---:|---:|---:|---:|
| 只给词 | 71 | 43.7%（32.4–54.9） | 48.2% | 26.7% | 29.6% |
| 词 + 一段用到它的聊天（3 条） | 66 | 56.1%（45.5–68.2） | 64.7% | 26.7% | 33.3% |
| 配对差（同 66 个词） | | **+13.6（+1.5，+25.8）**，14/5 | **+17.6（+3.9，+31.4）**，12/3 | 0（−26.7，+26.7），2/2 | |

没有空回答，所以端到端和有效回答准确率相同。只算给出了解释的回答（不含「不知道」），准确率为：只给词 62%，加语境 84%。

**按参考的来源拆开**（加语境）：参考是机器原词条、人工确认正确的 39 个词，对 72%；参考由人工写出或改写的 27 个词（含机器写错、机器丢掉、凭记忆列出的），对 33%。前者有偏差：词条本来就是同一个模型写的，它懂的词才容易写对。

**结论**：

1. **通用层：模型自带的知识只够一半。** 只给词 48%，加一段语境到 65%，提升显著。剩下的多是缩写和圈内说法，模型要么说不知道，要么只猜出大类。这一层正是联网核对能起作用的地方。【证实，样本小】
2. **本群层：模型基本不懂，语境也没帮上。** 15 个词只对 4 个，加语境不变，「不知道」从 47% 升到 60%。一段聊天不够推出本群含义，必须靠梗表。联网对这层也不该用（D-033）。【证实方向，样本 15 个】
3. **模型会老实说不知道。** 三成左右回答「不知道」，给出解释时多半是对的（加语境 84%）。这对上线有用：「不知道」可以作为查梗表或联网的触发信号。
4. 以后联网模块就用这一套题评测：只给词 / 词 + 语境 / 词 + 联网结果 / 词 + 梗表，同一批词配对比较。

**用量**：回答 137 次（入 9k、出 87k token，出含思考），判官 135 次（入 69k、出 1k）。台账新增 6 行。
